## Why

`elasticstack_kibana_security_exception_item.comments` is modeled today as an ordinary mutable list of `{ id (computed), comment }`. The Kibana exception-item API (`PUT /api/exception_lists/items`) does not support that model: it is append-only. `toUpdateRequest` in `internal/kibana/security_exception_item/models.go` sends every configured comment's text on every update and never sends `id`, so Kibana appends a fresh copy of each existing comment on every `terraform apply` — a real item has been observed growing 1 → 2 → 4 → 8 comments across three consecutive applies with no user-side change. Attempting to edit, reorder, or remove a comment through configuration is either silently dropped by Kibana (producing a `produced inconsistent result after apply` error) or rejected outright with `400 item "comments" are append only` when a new entry is not placed at the end.

Two conditional-replacement designs were evaluated and rejected (see `design.md`): passing `id` through plus a plan modifier that forces `-/+ destroy and replace` whenever the diff is not a pure trailing append (the issue body's proposal, and the independent implementation-research comment's recommendation). Both treat `comments` as an attribute Terraform fully owns. In practice analysts add comments directly in Kibana; after a refresh, Terraform's state holds the full server log while the user's configuration only ever listed the subset it cares about. Under either rejected design, that mismatch reads as a shrink and forces every subsequent apply to destroy and recreate the exception item just to converge a list Terraform never fully owned, dropping the exception for the duration of the replace, re-stamping every `created_by` to the API-key owner, and changing the item's generated id.

## What Changes

- **BREAKING**: `comments` becomes a computed-only attribute (`id`, `comment`, `created_at`, `created_by`) representing the full comment log Kibana has stored for the item, including comments added outside Terraform. `created_at` uses the same `2006-01-02T15:04:05.000Z` layout as the item's other audit timestamps. An empty log is null in state. Configurations that currently set `comments` will fail to apply. Users who still want those texts enforced move them onto `required_comments` and delete the `comments` block. The changelog is the only user-facing migration note.
- Add a new optional `required_comments` attribute: a list of comment-text strings that Terraform ensures are present somewhere in the log. It is a "must contain" set, not the log itself and not an exclusive list. Validated as non-empty, non-whitespace-only strings with no duplicate entries (exact, case-sensitive comparison). A stored text satisfies an entry whether or not Terraform wrote it.
- **Create**: POST `required_comments`, in configuration order, as `{comment}` entries with no `id`, when the list is non-null and non-empty; omit `comments` from the create body otherwise.
- **Update**: Before building the update request, compute `missing` as the `required_comments` texts not already present (by exact text) among the item's currently-stored comment texts, determined from a fresh read taken during apply (not from the planned `comments` value). If the fresh read cannot return the complete current log, abort with its diagnostic and do not send a PUT. When `missing` is empty, omit `comments` from the PUT body entirely — even when some other attribute changed. When `missing` is non-empty, append those texts in configuration order. Kibana 8.6.0 and later use only the missing texts; Kibana versions before 8.6.0 use every stored comment echoed with its `id` in stored order followed by the missing texts. A version-discovery diagnostic aborts before PUT. A stored text is never sent again without its `id`.
- **Plan**: `comments` is planned as unknown on create, when `required_comments` is unknown, and when any known required text is absent from state. Otherwise the prior state value is carried through unchanged, so reordering or removing a `required_comments` entry — which never touches the Kibana log — does not perturb `comments` in the plan.
- **No `RequiresReplace`** is added to either `comments` or `required_comments`. A comment-only change never destroys and recreates the exception item. A change to an existing immutable attribute (`space_id`, `item_id`, `list_id`, `type`, `namespace_type`) still replaces the resource under REQ-010, and the new item's initial comments are `required_comments` only.
- Removing a string from `required_comments` only stops Terraform from requiring it; the corresponding Kibana comment, if it had been created, is left in place. Terraform never issues a delete for an individual comment — the public API offers no such operation.

## Capabilities

### Modified Capabilities

- `kibana-security-exception-item`: `comments` becomes computed-only (full server log, including out-of-band comments); a new `required_comments` optional attribute drives an append-only reconciliation on create/update; no replacement is ever forced by comment changes.

## Impact

- **Affected code**: `internal/kibana/security_exception_item/schema.go` (new `required_comments` attribute; `comments` becomes `Computed`-only with new `created_at`/`created_by` nested attributes), `internal/kibana/security_exception_item/models.go` (comment-to-API mapping, missing-text computation, plan modifiers for `comments`), and the create/update/read paths (fresh read during update before building the PUT body).
- **State migration**: bump the resource schema version and upgrade existing v0 comment objects by adding null `created_at` and `created_by` keys. Keep prior `id` and `comment` values, and leave `required_comments` null; never infer required configuration from the historical full server log.
- **Acceptance tests**: `internal/kibana/security_exception_item/acc_test.go` and `testdata/TestAccResourceExceptionItem_Comments` still configure a `comments` block and must be rewritten. New cases cover version-specific update payload selection (8.5 uses echo-with-ids; 8.6+ uses the missing-only body), aborting before PUT when fresh-read or version discovery fails, no-op second apply, incremental append, removal-without-delete, edit-without-delete, reordering without replacement, out-of-band comment tolerance, an analyst-written text that already satisfies a requirement, state migration, and import behavior (see `tasks.md`).
- **Documentation**: tfplugindocs generates `docs/resources/kibana_security_exception_item.md` from schema descriptions. Those descriptions cover `required_comments` and the computed `comments` log. They do not include a migration snippet.
- **Canonical spec**: syncing this change replaces the `comments` stanza in `openspec/specs/kibana-security-exception-item/spec.md` with the schema refinement in the delta.
- **Changelog**: a breaking-change entry is the user-facing migration note; flagged in `tasks.md` for the implementer (`make` changelog tooling, not authored here).
- Out of scope: `elasticstack_kibana_security_exception_list` (no `comments` attribute today), editing or deleting a single existing comment (unsupported by the Kibana API), preserving `created_by`/`created_at` across a replacement triggered by an unrelated immutable attribute, enforcing comment order after create, and PR #3572 (the id-passthrough + conditional-`RequiresReplace` fix), which this proposal supersedes and which must not be merged.
