# Tasks

## 1. The provider's Kibana client can read and apply advanced settings, and Kibana's real behavior is confirmed

- [x] 1.1 Expose `GET` and `POST /api/kibana/settings` in the generated Kibana client through a paths-only overlay in `generated/kbapi` (design D1), and add a short section to `generated/kbapi/README.md` describing the overlay. Verified by an overlay-transform unit test that the paths and operation IDs are injected, and by regenerating at the pinned commit and confirming the change to `kibana.gen.go` is purely additive. If unrelated churn appears, use the hand-written wrapper fallback from the design's risk table and tell the user.
- [x] 1.2 Return a space's user-set settings keyed by setting name from a `kibanaoapi` wrapper, using the space-aware path (unprefixed for the default space), sending the `x-elastic-internal-origin: Kibana` header on every request (D1), and reporting HTTP 404 as not found (REQ-001, D5). Verified by `httptest` unit tests covering default and non-default space paths, the header, mixed value types (string, boolean, number, array, object), and 404. These tests are also the layer chosen for the unprefixed default-space path, since acceptance tests use random spaces (D8).
- [x] 1.3 Apply a set of changes in one bulk request from the wrapper, where a nil value resets a key, every request carries the internal-origin header (D1), 404 is reported distinctly, and Kibana failures (400 including a setting pinned by Kibana server configuration, 403, other statuses, transport errors) become error diagnostics carrying Kibana's message (design D2, D7). This task owns all wrapper-level error-mapping tests. Verified by `httptest` unit tests asserting the request body (including `null` resets and exact number preservation), the header, and each failure's diagnostic.
- [x] 1.4 Confirm against a live stack the behaviors the design assumes: a `null` change resets a key, a user value equal to its Kibana default is retained rather than dropped, and Kibana does not report a missing or deleted space on these routes (reads and writes succeed), which is why space existence comes from the spaces API. Also determine whether a minimum Kibana version applies and whether serverless supports the route (outcome: no floor found in the route source; behavior verified only on current stateful Kibana, so acceptance tests are gated through one shared helper to stateful deployments whose server version is 9.5.0 or later (the gate reads the acceptance stack's server version), because CI runs acceptance tests across a stack-version matrix that includes older stacks). Verified by acceptance tests that exercise the wrapper directly and pass on the latest stack, by a written report of all findings to the user at the gate before slice 2 begins (any result that contradicts the design or spec is raised there for a decision), and by the version and flavor gate being applied as a skip condition in every acceptance test of slices 2 to 7.

## 2. A user can declare string and JSON settings for a space and see them applied in Kibana

- [x] 2.1 Provide the `elasticstack_kibana_advanced_settings` resource, registered in `provider/plugin_framework.go`, in a new `internal/kibana/advancedsettings` package built on the Kibana resource envelope. It has `space_id` (default `default`, replacing the resource when changed), computed `id` equal to `space_id`, optional `string_settings` and `json_settings` (a map of normalized-JSON elements), the envelope's `kibana_connection` and `timeouts`, no import support, no schema version, and no attribute names that would conflict with a later global-settings addition (REQ-001, REQ-002, REQ-003, REQ-018; design D3, D4, D10). Verified by a schema and interface-contract unit test (including the `space_id` default and replace-on-change attributes), and by an early unit test that a map of normalized-JSON elements applies semantic equality, falling back to a plain `map(string)` with custom normalization if it does not. This unit test is also the layer chosen for the default-space scenario.
- [x] 2.2 Create applies every declared key in one request: `string_settings` values as strings, `json_settings` values with their JSON types (boolean, number, array, object, string), unrecognized keys passed through, nothing sent for an empty or omitted configuration, unmanaged settings in the space left untouched, and a failure stating that the space must exist, with nothing written, when a space other than `default` does not exist (REQ-004, REQ-005, REQ-009, REQ-010, REQ-019; D4, D6, D7). Verified by pure-conversion unit tests, a unit test of the space check (`default` never checked, a missing space reported, other spaces-API failures surfaced), acceptance tests, in a per-test random space, that Kibana holds the expected typed values, and an acceptance test creating with a nonexistent `space_id` that expects the error and asserts no setting was written. The acceptance assertions run together with the read-after-write from 2.3, which the envelope requires after every create.
- [x] 2.3 Record managed keys in state from Kibana after create: strings as strings, non-strings as JSON text, `json_settings` compared by semantic JSON equality, an omitted map staying null, and no diff on a following plan (REQ-012, REQ-013; D6). Verified by `refreshState` unit tests and an acceptance test that a second plan is empty.
- [x] 2.4 Settings in different spaces are independent, changing `space_id` replaces the resource, and every operation honors the resource's `kibana_connection` override when set (REQ-001, REQ-002, REQ-018). Verified by an acceptance test with two spaces declaring the same key with different values, an acceptance test that a changed `space_id` plans destroy-before-create, and an acceptance test using an explicit Kibana connection.
- [x] 2.5 Ship a self-contained example at `examples/resources/elasticstack_kibana_advanced_settings/resource.tf`, embedded long descriptions, generated resource documentation, and a changelog entry in the unreleased section of `CHANGELOG.md`. The documentation covers that only declared keys are managed and other settings are untouched, string versus JSON typing with examples (including settings that store JSON as a string), per-space scoping, that values are stored in state and must not contain secrets, and that two resources in one space overwrite each other's keys, naming `defaultIndex` and `elasticstack_kibana_default_data_view` (D9, D11). Verified by the example plan-only acceptance test passing, the docs generation check showing no diff, and the changelog entry being present.

## 3. A user gets clear plan-time errors for invalid keys and values

- [x] 3.1 Reject setting keys shorter than 1 or longer than 1024 characters in either map at plan time, without contacting Kibana (REQ-006). Verified by validator unit tests and an acceptance test expecting the validation error.
- [x] 3.2 Reject a key declared in both `string_settings` and `json_settings`, naming the key, while not checking overlap between different resources (REQ-007). Verified by a unit test of the resource-level validation and an acceptance test expecting the error.
- [x] 3.3 Reject invalid JSON, the JSON value `null`, and null entries in either map, advising that removing the key resets the setting, and re-validate values that were unknown at plan time before any settings request is sent at apply (REQ-008; D7). Verified by unit tests for each rejection and an acceptance test where a `json_settings` value comes from another resource's output and resolves to invalid JSON.

## 4. A user can change a managed setting, add keys, move a key between maps, or remove a key to reset it

- [x] 4.1 Update sends one request containing only keys that are new or whose value changed (compared with semantic JSON equality) plus resets for keys no longer declared in either map, sends nothing when there is no difference, applies a key that moves between `string_settings` and `json_settings` with its new type rather than resetting it, never changes settings the resource does not manage, and fails with the space-must-exist error when the space was deleted after the last refresh (REQ-011, REQ-019; D6). The resource documentation states that removing a key resets the setting to its Kibana default. Verified by `buildChanges` unit tests (including the move case), a unit test of the update path with a missing space, and acceptance tests that a changed value is applied, an added key is applied, a removed key returns to its Kibana default while other keys keep their values, a custom key moved from the string map to the JSON map is stored with the new type, and an unmanaged setting is unchanged, plus the documentation generation check showing no diff.

## 5. A user sees Terraform detect drift in managed settings

- [x] 5.1 An out-of-band change or reset of a managed key appears in the next plan and is corrected by apply, while out-of-band changes to settings the resource does not manage cause no drift (REQ-012). Verified by acceptance tests that edit Kibana through the wrapper between steps and assert the plan, using a refresh-and-expect-non-empty-plan step for the managed cases and an empty plan for the unmanaged case.
- [x] 5.2 A `string_settings` key whose Kibana value has become a non-string shows as drift using the value's JSON text, and `json_settings` values differing only in whitespace, object key order or number formatting show no drift (REQ-013). The resource documentation states the limitation that a string `"true"` and a boolean `true` are indistinguishable in drift detection. Verified by `refreshState` unit tests, an acceptance test that changes a custom key's type out of band, and the documentation generation check showing no diff.
- [x] 5.3 When a space other than `default` no longer exists according to the spaces API, refresh removes the resource from state without failing, even though Kibana still serves the space's earlier settings; the `default` space is never treated as missing, and a failed spaces lookup is surfaced as an error and never treated as missing (REQ-015). Verified by a unit test of the space check and an acceptance test that deletes the space out of band and asserts the refresh succeeds and the resource is removed from state.

## 6. A user can destroy the resource and have only its managed settings reset

- [x] 6.1 Destroy resets every managed key to its Kibana default in one request, leaves all other settings in the space unchanged, sends nothing when no keys are managed, and succeeds when a managed key was already reset outside Terraform (REQ-014; D6). The resource documentation states that destroy resets only the managed keys. Verified by acceptance tests using a custom destroy check that reads the space's settings through the wrapper to assert managed keys are gone and unmanaged keys remain, a unit test of the no-managed-keys case, and the documentation generation check showing no diff.
- [x] 6.2 Destroy succeeds without any settings request when the space was deleted outside Terraform (REQ-015). Verified by a unit test asserting no settings request is made for a missing space (the destroy path itself) and an acceptance test that deletes the space out of band in a `PlanOnly` step, so the harness's closing `terraform destroy -refresh=false` reaches the destroy path without a refresh, asserts it succeeds, and guards that the destroy ran. (A real `terraform destroy` refreshes first and removes the resource at refresh, which task 5.3 covers.)

## 7. A user who misconfigures a setting or lacks permission gets Kibana's error with clear guidance

- [x] 7.1 Operations fail with an error containing Kibana's message when Kibana rejects them (invalid value for a registered setting, a setting pinned by Kibana server configuration, a missing privilege) or the request fails, and when the changes actually sent include `string_settings` entries each error's detail also advises using `json_settings` for non-string values, but not when only `json_settings` entries were sent (REQ-016; D7). Wrapper-level error mapping is verified in 1.3. Verified by resource unit tests for the hint's presence and absence and an acceptance test that declares a boolean setting in `string_settings` and expects Kibana's error plus the hint.
- [x] 7.2 A failed create leaves the resource out of state, a failed update keeps the prior state, and a 404 from the settings route itself is surfaced as an error naming the missing route (REQ-017, REQ-020; D7). Verified by acceptance tests for a rejected create and a rejected update asserting the resulting state, and a resource unit test of the route-404 error mapping.
- [x] 7.3 Document the Kibana privilege required to write advanced settings (`manage_advanced_settings`, confirmed by a live 403), the `json_settings` hint behavior, that the settings routes are internal with no public contract, that settings can outlive a deleted space, that integers beyond the JavaScript safe range may show as drift, and what was verified (current stateful Kibana) versus not (older versions, serverless) (D9). Verified by the docs generation check showing no diff, the example plan-only test still passing, and the documented privilege name matching the live error message.
