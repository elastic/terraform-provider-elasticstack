## Context

Users managing concrete indices via `elasticstack_elasticsearch_index_template` + ILM rollover have no first-class way to update dynamic settings (e.g. `index.mapping.total_fields.limit`) on an already-created index, because index templates only apply settings at index-creation time. `elasticstack_elasticsearch_index_mappings` already established the "declared subset on an existing resource, no lifecycle ownership" pattern for mappings; this change applies the same pattern to settings.

The authoritative implementation-research comment (2026-09-07, confirmed 2026-10-06) is the scope baseline for this proposal. Its recommended approach (Approach A: shared `settings_keys.go`-owned attribute map + shared embeddable struct + `settings_json` escape hatch) is adopted as-is; the issue's own comment thread resolved every open design question the research comment raised, and those answers are incorporated directly as Decisions below.

## Goals / Non-Goals

**Goals:**
- Let Terraform update dynamic (runtime-changeable) settings on an existing concrete index without adopting the index's full lifecycle.
- Collapse the hand-sync between `settings_keys.go` (names only) and `index/index/schema.go` + `models.go` (types) into a single shared definition, consumed by both the existing `index` resource and the new resource.
- Provide an escape hatch (`settings_json`) for Elasticsearch dynamic settings not yet modeled as typed attributes, without making the typed-attribute list pointless.
- Keep destroy behavior simple and safe for production indices (fixed no-op).

**Non-Goals:**
- Generic `setting { name, value }` block, or a JSON-blob-only `settings` attribute as the sole interface. Rejected across all research runs in favor of typed attributes + a narrowly-scoped escape hatch.
- Static (creation-time-only) settings. `elasticstack_elasticsearch_index` already provides read-only drift detection for these; this resource only ever targets `DynamicSettingsKeys`.
- Cluster-level settings (`clients/elasticsearch/settings.go`) — out of scope.
- Index creation, deletion, aliases, mappings, or any other full-index-lifecycle concern.
- Wildcard-pattern-to-many-concrete-indices state modeling in one resource instance — deferred; callers use their own `for_each` over resolved concrete index names, as shown in the issue's example.
- Configurable destroy behavior — fixed no-op destroy is sufficient for v1.

## Decisions

These were resolved directly by `@tobio` across the issue comment thread and are treated as final for this proposal (human direction overrides the research comment's recommendation only where it narrows or clarifies it; here the two agree):

- **Shape**: typed attributes for each `DynamicSettingsKeys` entry (shared with `index/index`, not duplicated), plus a `settings_json` escape hatch. Not a generic `setting { name, value }` block, not a JSON-blob-only interface.
- **Attribute ownership**: `settings_keys.go` owns the full schema attribute definitions via `GetDynamicSettingAttributes() map[string]schema.Attribute` (corrected from the literal `map[string]resource.Attribute` named in the 2026-09-07 comment — confirmed 2026-10-06 as shorthand, not a design change), merged into each consuming resource's own schema map. This mirrors two existing in-tree precedents: `AccessAttributesResource()` (`internal/elasticsearch/security/apikey/attributes_common.go:104`) and `commonBlockAttributes()`/`mergeAttributes` (`internal/elasticsearch/snapshot/repository/schema.go:86,120`). Long attribute descriptions are carried as `//go:embed` Markdown files in the shared package, embedded with exact content and trailing-newline preservation so the descriptions remain byte-for-byte identical to their pre-refactor hand-declared form.
- **Embedding mechanism**: terraform-plugin-framework v1.19.0's struct-tag reflection supports an anonymously-embedded struct field (no `tfsdk` tag on the embedded field itself) and flattens its inner tagged fields into the parent schema; this pattern is already used elsewhere in this provider. `internal/elasticsearch/index/dynamicsettings.Model` is embedded anonymously in both `tfModel`s.
- **`index/index/reflectutil.go` dependency**: `GetFieldValueByTagValue`/`SetFieldValueByTagValue` currently only walk the immediate struct's fields (`field.Anonymous` is not handled), so an anonymously-embedded `dynamicsettings.Model` would be invisible to `toIndexSettings`/`hydrateAllSettingsFromRaw` without adding `field.Anonymous` recursion. This is the one shared, shipping-resource-touching change in this proposal; it must ship with isolated unit tests covering both the flat (current) and embedded (new) struct shapes. `reflectutil.go` is not the only direct-field scanner: `index/index/settings_read.go`'s `setTFModelField` and `pruneImportHydratedPlanFields` also iterate the struct's direct fields and would skip the embedded dynamic fields, breaking import hydration and pruning. Both must be updated to handle anonymous embedded structs, and their existing regression tests kept.
- **Migration timing**: migrating `index/index/schema.go`'s existing hand-declared dynamic attributes to `GetDynamicSettingAttributes()` happens in the **same PR** as the new resource (confirmed 2026-10-06), not as a follow-up. This is a sizing/risk tradeoff the maintainer accepted explicitly, not a design change — the migration must preserve existing attribute descriptions, plan modifiers, and behavior exactly (see REQ-UNCHANGED in the `elasticsearch-index` delta spec).
- **`settings_json` escape hatch scope**: permissive on keys outside `AllSettingsKeys` (so new Elasticsearch dynamic settings work without a provider release), but rejects at plan time any key that is a literal `StaticSettingsKeys` match. Scoping the hatch to only already-known dynamic keys "would make the escape hatch pointless" (per `@tobio`, 2026-09-04); strict-on-static, permissive-on-unknown resolves the tension raised in the 2026-09-07 research comment between catching typos and allowing forward compatibility — forward compatibility wins.
- **Typed vs `settings_json` overlap**: a setting may be declared via a typed attribute or via `settings_json`, never both. At plan time, after canonicalizing key spellings (e.g. `number_of_replicas` vs `index.number_of_replicas`), any `settings_json` key matching a configured typed attribute is rejected, since Elasticsearch stores a single value and the plan could never converge. When a `settings_json` value (or a typed attribute's value) is unknown at plan time, the shape and overlap checks on that value are deferred (no error emitted) rather than failing on the unknown value — unknown setting values must never cause spurious empty-declaration errors.
- **Import**: import hydrates only the known dynamic typed attributes from the API response and leaves `settings_json` unset, because hydrating `settings_json` from the full response would adopt static/metadata keys (e.g. `index.number_of_shards`, `index.uuid`) that a later narrowed config would send as `null`, which Elasticsearch rejects. Hydration is keyed on an import-specific private-state flag set by a custom `ImportState` and cleared by the first read — never on an empty tracked set, which is also reachable via a legitimate config after an external reset of the last tracked setting (Elasticsearch drops the key from persisted settings). `settings_json = {}` is additionally rejected at plan time as it declares nothing — but an index-only configuration (`index` set, no typed attribute, no `settings_json`) is valid: the earlier at-least-one-setting validator is removed, create verifies the target index exists and records the resource in state with the computed `id` without issuing a settings PUT, removing the last/all declared settings sends `null` for the previously tracked keys only, and repeated refresh of an empty declared subset adopts nothing. Ownership is presence in state; a tracked setting missing from the API response is nulled (drift shown) and re-established by config on the next apply.
- **`settings_json` shape**: flat dotted keys only. Nested objects are rejected at plan time so that overlap validation, diffing and read all operate on the same top-level keys as `GetIndex`'s flat response. Explicit JSON `null` values are rejected too; a setting is reset by omitting it, which avoids a conflict between configured reset markers and the read rule that drops keys Elasticsearch no longer reports. On read, API string values are reconciled to the declared scalar type (as in `index/index/settings_read.go`) to avoid false drift from `jsontypes.Normalized` comparing `20000` and `"20000"`. Array values are supported (operator instruction, 2026-10-06): a `settings_json` value may be an array of string/number/boolean elements, including an empty array; array elements that are objects or `null` are rejected at plan time, consistently with the flat non-null contract. On read, arrays arriving as real JSON arrays or as JSON-encoded array strings are reconciled against the declared element types, preserving element order and drift, never silently dropping a valid tracked array and never changing string elements to numbers accidentally. The typed `query_default_field` decodes JSON-encoded string arrays via the existing `stringSliceFromAny` precedent in the `index` resource.
- **Validator precedent**: `internal/elasticsearch/queryrulesets/validators.go`'s `jsontypes.Normalized`-parsing plan-time validator pattern (e.g. `criteriaValuesJSONValidator`) is the template for the new `settings_json` validator — parse the JSON object's top-level keys and emit an attribute error for any exact `StaticSettingsKeys` match.
- **Scope per resource instance**: exactly one concrete (`for_each`-resolved) index name. `GetIndex` assumes a concrete name; wildcard expansion to many indices within one instance's state is explicitly deferred to future work, not attempted here.
- **Date math**: not applicable. This resource targets settings on an *existing* index; there is no creation step where a date-math expression would need resolving.
- **Wildcard index names**: `index` must be a concrete index name. `GetIndex` looks the name up as a key in the Elasticsearch response (`indices[name]`), and Elasticsearch keys that map by concrete name, so a wildcard or alias is not resolved and would be reported as not found — even if the pattern matches exactly one index. No wildcard-matching logic is added. Callers needing settings across many concrete indices use `for_each` over names resolved outside the resource (e.g. via the `indices` data source), each getting its own instance, per the issue's example.
- **Destroy behavior**: fixed no-op, identical in spirit to `indexmappings`' no-op delete — removing the resource from configuration does not revert or clear settings on the live index. No configurable destroy behavior in v1.
- **Null semantics**: setting a previously-declared typed attribute (or a `settings_json` key) to `null` on a later apply must behave consistently with `elasticstack_elasticsearch_index`'s existing `update.go` (`updateSettings`): removed dynamic settings are explicitly sent as `null` to the Elasticsearch settings API (its null-to-reset semantics), not merely dropped from Terraform's tracking.
- **Identity**: `id` is `<cluster_uuid>/<index_name>`, matching `indexmappings/create.go:49` (`client.ID(ctx, indexName)`) → `elasticsearch_scoped_client.go:112` (`ClusterID` + resource ID → `CompositeID`). No new client code needed; `GetIndex`/`UpdateIndexSettings` (`internal/clients/elasticsearch/index.go:114,134`) are reused as-is.
- **Shared location**: `DynamicSettingsKeys`/`StaticSettingsKeys`/`AllSettingsKeys` already live in `internal/elasticsearch/index/settings_keys.go`, consumed by both `index/index` and the new resource — this satisfies the "single shared location" instruction from the 2026-09-04 comment without further relocation.

- Confirm `GetDynamicSettingAttributes()` should return `map[string]schema.Attribute`, not the literal `map[string]resource.Attribute` named in the 2026-09-07 comment (non-blocking, likely just shorthand).
- Should migrating `index/index/schema.go`'s existing hand-declared dynamic attributes to `GetDynamicSettingAttributes()` happen in the same PR as the new resource, or as a follow-up? Affects PR sizing/risk, not the design.

Both of the above were answered during this run (2026-10-06): `map[string]schema.Attribute` is confirmed, and the migration ships in the same PR. They are retained here verbatim per the research-comment carry-forward requirement; the Decisions section above records the resolution.

## Risks / Trade-offs

- [Risk] The `reflectutil.go` anonymous-field recursion change touches the shipping `index` resource's existing reflection-based settings round-trip. → Mitigation: isolate the change with unit tests covering both pre-existing flat struct fields and the new embedded struct shape before wiring either resource to depend on it.
- [Risk] Migrating `index/index/schema.go`'s ~30 attributes to the shared function in the same PR as the new resource is itself a regression-risk refactor — attribute equality (descriptions, plan modifiers, validators) must not change for existing `elasticstack_elasticsearch_index` users. → Mitigation: a byte-for-byte (or semantically-equal) schema diff check / existing unit and acceptance test coverage for `index/index` must pass unchanged; no attribute description or plan-modifier wording changes beyond what's strictly necessary to make the function shared.
- [Risk] `settings_json` being permissive on unknown keys means a typo in a future Elasticsearch-only setting name is not caught at plan time (only a literal `StaticSettingsKeys` match is rejected). → Accepted trade-off per `@tobio`'s explicit instruction (2026-09-07): forward compatibility with new ES dynamic settings outweighs catching typos for keys the provider doesn't know about yet.
- [Risk] Scoping to one concrete index per instance means users with genuinely dynamic (unknown-at-plan-time) sets of indices must discover index names via a separate data source and `for_each` over them themselves. → Accepted per `@tobio` (2026-09-04/07): this matches the issue's own example and keeps `GetIndex`'s concrete-name assumption intact; wildcard state modeling is deferred.
