## Why

The Elasticsearch `searchable_snapshot` ILM action supports `force_merge_on_clone` (bool, default `true`, GA since 9.2.1 — [elastic/elasticsearch#137375](https://github.com/elastic/elasticsearch/pull/137375), backported to `9.2.1`/`9.3.0`; `9.2.0` does not have it) alongside `force_merge_index` and `snapshot_repository`. It controls whether the `force_merge_index` merge runs on a temporary clone of the managed index (the default) or directly on the index itself. Per elastic/elasticsearch#133954, if the clone-and-force-merge sequence is interrupted (busy master, cluster load) before the clone is promoted and cleaned up, the resulting snapshot can carry a permanent `index.lifecycle.skip: true` setting. When later restored, the mounted index gets stuck outside any ILM phase and requires manually clearing `index.lifecycle.skip` via `_settings` before ILM evaluates it again. Setting `force_merge_on_clone: false` skips the clone step and avoids this failure mode for policies that don't need the force-merge (e.g. already-optimized restored data).

Elasticsearch also rejects any non-null `force_merge_on_clone` when `force_merge_index = false` (`SearchableSnapshotAction`'s constructor throws `[force_merge_on_clone] is not allowed when [force_merge_index] is [false]`), so the two attributes are not independent — this proposal must specify how that interaction is handled, not just add the new attribute in isolation.

`elasticstack_elasticsearch_index_lifecycle`'s `searchable_snapshot` block (used identically in `hot`, `cold`, and `frozen`) only exposes `snapshot_repository` and `force_merge_index` today, so `force_merge_on_clone` cannot be set from Terraform and is stuck at the Elasticsearch default.

## What Changes

- Add `force_merge_on_clone` (bool, optional + computed, default `true`) to the `searchable_snapshot` action block, available in `hot`, `cold`, and `frozen` phases (same block shape everywhere).
- Gate `force_merge_on_clone` behind a `9.2.1` minimum-version check using the existing `ilmActionSettingOptions` version-gating mechanism (same pattern as `shrink.allow_write_after_shrink`'s `8.14.0` gate): a non-default value on an unsupported server returns an error diagnostic; the default value is silently omitted from the payload.
- Reject, at plan time, any configuration that sets `force_merge_on_clone` (to any value) while `force_merge_index = false`, since Elasticsearch itself rejects that combination. Implement this with the repo's existing `internal/utils/validators` "conditional" validator framework (`Condition`/`ForbiddenIfDependentPathExpressionOneOf` in `internal/utils/validators/conditional.go`), extended with a boolean-dependent-value variant — that framework already implements `validator.Bool`/`validator.Object` for "forbid this attribute when a sibling's value is X," but today only supports string-typed dependents, so a small extension (or a new sibling constructor built on the same `Condition`/`dependentEvaluation` plumbing) is needed to compare against a `types.Bool` sibling. This reuses an established pattern instead of adding a new validator type from scratch.
- At expand time, omit `force_merge_on_clone` from the outbound payload whenever `force_merge_index` resolves to `false`, regardless of the schema's computed default, so the Computed default never gets sent in a combination Elasticsearch rejects.
- Change the ILM policy write path (`PutIlm` in `internal/clients/elasticsearch/ilm.go`) to submit the marshaled policy JSON via the typed client's `.Raw()` body instead of unmarshaling into `putlifecycle.Request` and using `.Request()`. This is required because the vendored `go-elasticsearch` typed struct for the searchable-snapshot action (and the upstream `elasticsearch-specification` it is generated from) does not model `force_merge_on_clone` yet; round-tripping through the typed struct would silently drop the field before it reaches Elasticsearch. `ClearILMPolicyFromIndices` in the same file already uses this `.Raw()` pattern for the same typed-struct-gap reason, so this is not a new pattern in this package.
- Change the ILM policy read path (`GetIlm` in the same file) to avoid decoding the GET Lifecycle response through the same typed `SearchableSnapshotAction` struct. The write-side fix alone is not sufficient: `GetIlm` currently calls `.Do(ctx)`, which decodes the response directly into `types.Lifecycle`, whose `SearchableSnapshotAction` field has the identical gap, so a `force_merge_on_clone` value that was successfully written would be silently dropped again on the very next read — including the read-after-write that create/update always perform — leaving state showing the default instead of the configured value. `GetIndicesWithILMPolicy` in the same file already uses `.Perform(ctx)` plus a manual, partial JSON decode for the analogous reason (the typed `Lifecycle` struct doesn't expose `in_use_by`), so `GetIlm` should follow that same precedent.
- Extend `TestAccResourceILMSearchableSnapshotPhases` with an additional `9.2.1`-gated test step (not a new test function) exercising `force_merge_on_clone`, following the existing `SkipFunc: versionutils.CheckIfVersionIsUnsupported(...)` convention used elsewhere in `acc_test.go`.
- File an upstream tracking issue against `elastic/elasticsearch-specification` so the `.Raw()` bypass in `PutIlm` can be reverted once the typed struct models `force_merge_on_clone` (follow-up task, not a blocker for this change).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `elasticsearch-index-lifecycle`: add a new version-gated `searchable_snapshot.force_merge_on_clone` setting (extends REQ-022–REQ-025's version-gating pattern), its interaction constraint with `force_merge_index = false`, and document both the `PutIlm` write-path change from the typed `.Request()` call to `.Raw()` and the `GetIlm` read-path change away from the typed response decode, so the setting round-trips correctly.

## Impact

- `internal/elasticsearch/index/ilm/constants.go` — add `attrForceMergeOnClone`.
- `internal/elasticsearch/index/ilm/schema_actions.go` — add the attribute to `blockSearchableSnapshot()` and `blockSearchableSnapshotInFrozenPhase()`, plus the new bool-sibling-value validator rejecting `force_merge_on_clone` when `force_merge_index = false`.
- `internal/utils/validators/conditional.go` — extend the dependent-value evaluation (`evaluateStaticPath`/`evaluatePathExpression`, currently hardwired to `types.String`) to support a `types.Bool` dependent, or add a small sibling constructor built on the same `Condition` plumbing, so it can express "forbidden when sibling bool equals `false`."
- `internal/elasticsearch/index/ilm/attr_types.go` — add the attribute to `searchableSnapshotObjectType()`.
- `internal/elasticsearch/index/ilm/expand.go` — register the setting in `ilmActionSettingOptions` (`def: true`, `minVersion: 9.2.1`); wire it into the `ilmActionSearchableSnapshot` case of `expandPhase`, and omit it from the outbound action map whenever `force_merge_index` is `false`.
- `internal/clients/elasticsearch/ilm.go` — swap `PutIlm` to use `.Raw()` instead of `.Request(&putlifecycle.Request{...})`; drop the now-unused typed unmarshal (and the `putlifecycle` import) if nothing else in the function needs it. Also change `GetIlm` to use `.Perform(ctx)` plus a manual, partial JSON decode (following `GetIndicesWithILMPolicy`'s existing pattern in the same file) instead of `.Do(ctx)`'s typed `types.Lifecycle` decode, so action fields the typed client doesn't model (like `force_merge_on_clone`) survive the read path too.
- `internal/elasticsearch/index/ilm/policy.go` — update `readPolicyIntoModel` for `GetIlm`'s new return shape; the existing re-marshal-then-unmarshal step that builds a generic `actions map[string]map[string]any` (`policy.go:102-113`) may become unnecessary if `GetIlm` now returns actions already in that shape.
- `internal/elasticsearch/index/ilm/flatten.go` — add a `case ilmActionSearchableSnapshot` (the action currently falls through the generic `default:` case) that backfills `force_merge_on_clone = true` when the key is absent from the read action map and `force_merge_index` is `true`, mirroring the existing `ilmActionShrink`/`allow_write_after_shrink` fallback (`flatten.go:85-90`). Elasticsearch only serializes `force_merge_on_clone` when it was explicitly set (the field is `@Nullable` server-side), so a plain passthrough would otherwise leave a `null` in state for this Computed attribute whenever left at its default.
- `internal/elasticsearch/index/ilm/acc_test.go` — add a package-level `searchableSnapshotForceMergeOnCloneMinSupportedVersion = version.Must(version.NewVersion("9.2.1"))` near the other version vars, plus a new gated step in `TestAccResourceILMSearchableSnapshotPhases` and any needed `testdata` fixtures.
- `openspec/specs/elasticsearch-index-lifecycle/spec.md` — extend REQ-022–REQ-025 (or add a new requirement) and the `searchable_snapshot` schema block documentation; update generated provider docs for the resource.
- Follow-up (outside this PR): file an issue against `elastic/elasticsearch-specification` requesting `force_merge_on_clone` support in the generated `SearchableSnapshotAction` type.
