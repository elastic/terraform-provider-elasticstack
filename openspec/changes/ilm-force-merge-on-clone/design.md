## Context

Elasticsearch's `searchable_snapshot` ILM action accepts `snapshot_repository` (required), `force_merge_index` (default `true`), and `force_merge_on_clone` (default `true`, GA since Elasticsearch `9.2.1`). `force_merge_on_clone` controls whether the `force_merge_index` merge happens on a temporary clone of the managed index (default behavior) or directly on the index. Per elastic/elasticsearch#133954, an interrupted clone-and-merge sequence can leave a snapshot permanently marked `index.lifecycle.skip: true`; setting `force_merge_on_clone: false` avoids that code path.

The field landed in [elastic/elasticsearch#137375](https://github.com/elastic/elasticsearch/pull/137375), labeled `v9.2.1`/`v9.3.0` (not `v9.2.0`) and gated server-side behind `TransportVersion.fromName("ilm_searchable_snapshot_opt_out_clone")`; `9.2.0` does not parse this field at all, so `9.2.1` is the correct minimum version, not `9.2.0`.

`SearchableSnapshotAction`'s Java constructor also enforces a cross-attribute constraint that this design must account for: `if (forceMergeIndex == false && forceMergeOnClone != null) { throw new IllegalArgumentException("[force_merge_on_clone] is not allowed when [force_merge_index] is [false]"); }`. Since `force_merge_on_clone` is proposed as Optional+Computed with a static `true` default (mirroring `force_merge_index`), naively sending the computed default whenever `force_merge_index = false` would trip this validation with an opaque 400 from the Put Lifecycle API — and this repo's own `TestAccResourceILMSearchableSnapshotPhases` acceptance fixtures already configure `force_merge_index = false` in both their `create` and `update` steps, so this isn't a hypothetical edge case.

Separately, on the read side, `force_merge_on_clone` is a `@Nullable Boolean` in `SearchableSnapshotAction` and its `toXContent` only serializes the field when non-null (`if (forceMergeOnClone != null) { builder.field(FORCE_MERGE_ON_CLONE.getPreferredName(), forceMergeOnClone); }`) — unlike `force_merge_index`, which is a non-nullable primitive `boolean` and is always echoed back. This means the Get Lifecycle response genuinely omits `force_merge_on_clone` whenever it wasn't explicitly set (not merely a client-decoding gap), so a naive generic-map passthrough on read would leave this Computed attribute as `null` in state instead of its `true` default.

`elasticstack_elasticsearch_index_lifecycle`'s `searchable_snapshot` block (same shape in `hot`, `cold`, and `frozen`) currently only exposes `snapshot_repository` and `force_merge_index`. The action round-trips through a generic `map[string]any` (`models.Action`, `internal/models/index.go:100`) on the Terraform side, but the vendored `go-elasticsearch` client's typed struct for this action (`typedapi/types/searchablesnapshotaction.go`) does not model `force_merge_on_clone` either, and neither does the upstream `elasticsearch-specification` (`specification/ilm/_types/Phase.ts`, checked at HEAD of `main`). Terraform-only schema wiring would silently no-op against the real API: `PutIlm` (`internal/clients/elasticsearch/ilm.go:35-46`) marshals the generic policy to JSON, then unmarshals it into a typed `putlifecycle.Request` before calling `.Request(&req)`; the typed struct's `UnmarshalJSON` silently drops unrecognized keys, so `force_merge_on_clone` would be accepted into Terraform state but never reach Elasticsearch.

This same typed-struct gap exists symmetrically on the **read** side and must be fixed together with the write side, not instead of it. `GetIlm` (`internal/clients/elasticsearch/ilm.go:53-71`) calls `typedClient.Ilm.GetLifecycle().Policy(policyName).Do(ctx)`, which decodes the HTTP response body directly into a typed `*types.Lifecycle`. Its `Policy.Phases.*.Actions.SearchableSnapshot` field is `*types.SearchableSnapshotAction` — the identical struct confirmed above — and that struct's hand-rolled `UnmarshalJSON` (`typedapi/types/searchablesnapshotaction.go:40-84`) is a token-scanning switch over exactly `force_merge_index` and `snapshot_repository`; any other key, including `force_merge_on_clone`, is silently discarded during this decode. `readPolicyIntoModel` (`internal/elasticsearch/index/ilm/policy.go:102-113`) later re-marshals `phase.Actions` to JSON and unmarshals it into a generic `map[string]map[string]any` for `flattenPhase`, but by then the field is already gone — the generic-map step is downstream of the lossy typed decode, not a replacement for it. Practically, this means a write-only fix to `PutIlm` would still lose `force_merge_on_clone` on every read-after-write (required by the create/update flow, see REQ-011–REQ-012) and on every subsequent `terraform plan`/refresh, producing state drift or a "provider produced inconsistent result after apply" error even though the value was correctly written to Elasticsearch.

This design was produced by a prior implementation-research pass on the linked issue, which evaluated two approaches (below) and got explicit sign-off from `@tobio` on the recommended one, including the ES version floor and the acceptable scope of the `PutIlm` change. The `GetIlm` read-path fix (Approach C, Decisions) was added afterward, during code review of this proposal, once it was established that the write-only fix alone does not make the feature round-trip through Terraform state; it follows the same reasoning and precedent `@tobio` already signed off on for `PutIlm`.

## Goals / Non-Goals

**Goals:**

- Let practitioners set `force_merge_on_clone = false` on `hot`, `cold`, and `frozen` `searchable_snapshot` blocks, and have that value actually reach Elasticsearch's ILM policy.
- Gate the new setting on Elasticsearch `9.2.1`, consistent with the existing `ilmActionSettingOptions` version-gating mechanism (e.g. `attrAllowWriteAfterShrink` at `8.14.0`).
- Keep the default (`true`) behavior unchanged and never send the field when unsupported and left at its default.
- Ensure the configured value round-trips correctly through read-after-write and subsequent `terraform plan`/refresh cycles, not just through the initial write — a value that writes successfully but reads back as the default is not a working feature.
- Never submit a payload combination Elasticsearch itself rejects: `force_merge_on_clone` must not be sent (or configured) when `force_merge_index = false`, and existing configurations that already set `force_merge_index = false` (e.g. this repo's own acceptance fixtures) must keep working unmodified after this change ships.

**Non-Goals:**

- `replicate_for` / `total_shards_per_node` on `searchable_snapshot` — other documented options, not requested here.
- Changing the default of `force_merge_index` or `force_merge_on_clone` (both stay Elasticsearch's default of `true`).
- Any remediation tooling for indices already stuck with `index.lifecycle.skip: true`.
- A broader `PutIlm` / `GetIlm` refactor beyond the minimal typed-struct bypass needed on each side (described below). This includes bypassing `GetIlm`'s typed decode for the ILM GET response — that is in scope, since without it the feature cannot round-trip through Terraform state at all (see Context); what's out of scope is any wider restructuring of `PutIlm`/`GetIlm` beyond what's needed to fix this gap.
- Actually filing/landing the upstream `elasticsearch-specification` issue — tracked as a follow-up task, not part of this change's implementation.

## Approaches considered

These were evaluated during research prior to this proposal and are treated as settled; they are recorded here for context, not re-opened for exploration.

### Approach A — Terraform-only schema/expand wiring (rejected)

Mirror `force_merge_index`: add `attrForceMergeOnClone` as a `BoolAttribute` (Optional+Computed+Default `true`) in `blockSearchableSnapshot()` and `blockSearchableSnapshotInFrozenPhase()`, add it to `searchableSnapshotObjectType()`, include it in `expandAction(...)`.

**Rejected because** `PutIlm` unmarshals the generic policy into a typed `putlifecycle.Request` before calling `.Request(&req)`; the generated `types.SearchableSnapshotAction` only declares `ForceMergeIndex` / `SnapshotRepository`, and its `UnmarshalJSON` silently drops unrecognized keys. Upstream `elasticsearch-specification`'s `Phase.ts` lacks the field too, so this gap can't be closed by only touching Terraform code — Approach A would compile, store the value in state, and never reach Elasticsearch, i.e. a silent no-op.

### Approach B — Same Terraform wiring, plus bypass the typed struct for `PutIlm` only (rejected as incomplete)

Everything from Approach A, plus send the marshaled policy JSON via the raw body path instead of `.Request()`:

```go
_, err = typedClient.Ilm.PutLifecycle(policy.Name).Raw(bytes.NewReader(policyBytes)).Do(ctx)
```

`PutLifecycle.Raw(io.Reader)` exists on the typed client (`typedapi/ilm/putlifecycle/put_lifecycle.go:115`), and `.Do()` gives the raw body precedence over `.Request()` (same file, line 146) when both are set — in practice this means dropping the `.Request(&req)` call and the preceding typed unmarshal entirely, and only ever calling `.Raw(...)`. This is not a new pattern in this package: `ClearILMPolicyFromIndices` (`internal/clients/elasticsearch/ilm.go:118-135`) already uses `.Raw()` on `Indices.PutSettings()` for the identical reason (a typed-struct gap).

**Rejected as insufficient on its own** because it only fixes the write path. `GetIlm` (`internal/clients/elasticsearch/ilm.go:53-71`) decodes the GET Lifecycle response into the same typed `types.SearchableSnapshotAction` struct, which has the identical gap (see Context). A write-only fix would let `force_merge_on_clone` reach Elasticsearch successfully, then silently lose it again on the very next read — including the read-after-write that `Create`/`Update` always performs — leaving Terraform state showing the default instead of the configured value.

### Approach C — Bypass the typed struct on both `PutIlm` and `GetIlm` (chosen)

Everything from Approach B, plus change `GetIlm` to avoid decoding the GET Lifecycle response through `types.Lifecycle`'s typed action structs. Concretely: call `typedClient.Ilm.GetLifecycle().Policy(policyName).Perform(ctx)` to get the raw `*http.Response` instead of `.Do(ctx)`, and decode the subset of the body the provider needs (`modified_date`, `policy._meta`, and each phase's `min_age`/`actions`) into local structs that leave `actions` as `map[string]map[string]any` rather than a typed `IlmActions`. This is not a new pattern either: `GetIndicesWithILMPolicy` (`internal/clients/elasticsearch/ilm.go:73-111`) already uses `.Perform(ctx)` plus a manual, partial JSON decode for the identical reason — "the typed client's generated `Lifecycle` struct does not expose `in_use_by`" (see that function's doc comment).

Purely generic decoding is not quite sufficient on its own, though: because `force_merge_on_clone` is only serialized by Elasticsearch when explicitly set (see Context), `flattenPhase` needs a `case ilmActionSearchableSnapshot` — analogous to the existing `ilmActionShrink`/`allow_write_after_shrink` fallback at `flatten.go:85-90` — that backfills `force_merge_on_clone = true` in the flattened map when the key is absent from a read and `force_merge_index` is `true`. When `force_merge_index` is `false`, no backfill is applied (see Approach D below), since Elasticsearch disallows a non-null value in that case.

### Approach D — Enforce the `force_merge_index = false` interaction via the existing `internal/utils/validators` conditional framework (chosen)

`SearchableSnapshotAction`'s constructor throws when `force_merge_index == false` and `force_merge_on_clone != null` (see Context), so the schema needs to (a) stop a user from configuring `force_merge_on_clone` alongside `force_merge_index = false`, and (b) never let the Computed `true` default get sent to the API in that combination regardless of what the user configured.

This repo already has a validator framework built for exactly this shape of constraint — `internal/utils/validators/conditional.go`'s `Condition` type, which implements `validator.Bool`/`validator.Object` and provides `ForbiddenIfDependentPathExpressionOneOf(dependentPath, allowedValues []string)` ("forbid this attribute when a sibling equals one of these values"). It is a better fit than the codebase's other cross-attribute validators, which are all presence-only: `objectvalidator.ConflictsWith`/`AlsoRequires`/`ExactlyOneOf` (from `terraform-plugin-framework-validators`, used throughout `schema_actions.go`, e.g. the existing `attrSnapshotRepository` `AlsoRequires` at `schema_actions.go:224`) only check whether a sibling is null or non-null — none of them can express "conflicts only when the sibling equals `false`," which is what's needed here, and `boolvalidator.Equals` (the one bool-aware validator the library ships) only compares an attribute to a static constant, not to a sibling's value.

`Condition`'s dependent-value evaluation (`evaluateStaticPath`/`evaluatePathExpression`) is currently hardwired to read the dependent attribute as `types.String` and compare against a `[]string` — every existing call site in the repo (`attrMode`, panel-type enums, etc.) uses a string-typed dependent. None uses a bool sibling like `force_merge_index`. So this design still requires a small, scoped extension: either add a `types.Bool`-dependent case to the same `dependentEvaluation`/`valueValidator` machinery (reusable for any future bool-conditional need), or add one small standalone constructor analogous in shape to `ForbiddenIfDrilldownVariantSiblingNestedPresent` but keyed on the sibling's boolean value instead of its presence. Either way, this reuses established plumbing instead of inventing a new validator type from scratch.

Independently of the schema-level validator (which only catches user-authored config), `expandAction`'s `ilmActionSearchableSnapshot` case must also omit `force_merge_on_clone` from the outbound action map whenever `force_merge_index` resolves to `false` — this is what actually prevents the Computed `true` default from ever being sent in the rejected combination, since the validator alone doesn't stop the framework from materializing a default.

## Decisions

- **Bypass the typed request path in `PutIlm`.** Confirmed acceptable by `@tobio`: "Moving off the typed path is fine." This affects all ILM policy writes through this provider, not just `searchable_snapshot`, but the payload is still built from the same `models.Policy` marshaling used today, so this is a transport-layer change, not a data-shape change.
- **Also bypass the typed decode in `GetIlm`.** Added during review of this proposal: the write-side fix alone does not make the feature work, because `GetIlm`'s `.Do(ctx)` decode goes through the same `types.SearchableSnapshotAction` gap on the way in. Without an analogous read-side fix, a correctly-written `force_merge_on_clone: false` would be silently reverted to the default on the very next read (including the mandatory read-after-write in create/update), producing state drift. This uses the same `.Perform(ctx)` plus manual-decode pattern already established by `GetIndicesWithILMPolicy` in the same file, so it is not a new technique for this codebase — see Approach C.
- **Version gate at `9.2.1`, not `9.2.0`.** Confirmed by `@tobio`: the provider's supported Elasticsearch floor is `8.0+`, and a `9.2.x` minVersion gate on `force_merge_on_clone` is required (the field is GA only from `9.2.1` onward — see Context for the exact source PR/labels). Implemented via the existing `ilmActionSettingOptions` map with `def: true, minVersion: version.Must(version.NewVersion("9.2.1"))`, following the `attrAllowWriteAfterShrink` (`8.14.0`) precedent — a non-default (`false`) value on an unsupported server is a hard error diagnostic, not a silent drop.
- **Enforce the `force_merge_index = false` interaction with a schema validator plus an expand-time omission, not version-gating alone.** Added during review of this proposal, once it was established that Elasticsearch rejects a non-null `force_merge_on_clone` when `force_merge_index = false` (see Context). The existing `ilmActionSettingOptions`/version-gate mechanism only compares an attribute to its own default in isolation; it has no notion of a sibling attribute's value, so this cross-attribute constraint needs its own handling — see Approach D.
- **Backfill the read-side default for `force_merge_on_clone` in `flatten.go`, mirroring `allow_write_after_shrink`.** Also added during review: because Elasticsearch only echoes `force_merge_on_clone` back when it was explicitly set (see Context), a generic passthrough would otherwise show `null` in state for a Computed attribute whenever the value was left at its default — see Approach C.
- **Test as an extension of the existing test, not a new one.** Confirmed by `@tobio`: add a new `SkipFunc`-gated step to `TestAccResourceILMSearchableSnapshotPhases` rather than a separate test function. Note: the `searchableSnapshotForceMergeUpdateVersionLimit` / line-425 `SkipFunc` convention in `acc_test.go` is currently used by `TestAccResourceILMFrozenPhase`, not by `TestAccResourceILMSearchableSnapshotPhases` (which today has no version-gated step at all) — the new step should follow that same `SkipFunc: versionutils.CheckIfVersionIsUnsupported(...)` convention, just applied to a different test function than the one it's currently used in.
- **File the upstream issue as a follow-up, not a blocking task.** The `.Raw()`/typed-decode bypass on both `PutIlm` and `GetIlm` is intentionally temporary; once `elasticsearch-specification` and the generated `go-elasticsearch` client model `force_merge_on_clone`, both can revert to the typed path. Filing that issue is tracked in `tasks.md` but does not block merging this change's implementation.

## Risks / Trade-offs

- **[Risk] `PutIlm` losing typed-request validation for all ILM writes**, not just `searchable_snapshot`. Mitigation: the payload is still constructed from the same `models.Policy` → JSON marshal used today; only the transport call changes from `.Request()` to `.Raw()`. Elasticsearch itself still validates the payload server-side, same as any other `.Raw()` call in this codebase (e.g. `ClearILMPolicyFromIndices`).
- **[Risk] `GetIlm` losing typed-response parsing for all ILM reads**, not just `searchable_snapshot`. Mitigation: scope the manual decode to the fields the provider actually consumes (`modified_date`, `_meta`, per-phase `min_age`/`actions`), mirroring the narrow, targeted decode `GetIndicesWithILMPolicy` already does for `in_use_by`, rather than hand-rolling a full replacement for `types.Lifecycle`.
- **[Risk] This is a workaround for an upstream gap that could resurface if `elasticsearch-specification` changes shape** before the field is added. Mitigation: filing the upstream tracking issue (see `tasks.md`) creates a paper trail to revert both bypasses once upstream support lands.
- **[Trade-off] Version-gating adds one more entry to `ilmActionSettingOptions`** that must be kept in sync with Elasticsearch's own version support matrix. This mirrors the existing pattern for `rollover.max_primary_shard_docs` (`8.2.0`), the `rollover.min_*` settings (`8.4.0`), and `shrink.allow_write_after_shrink` (`8.14.0`), so it is consistent with how the provider already manages this class of risk.
- **[Risk] Extending `internal/utils/validators/conditional.go`'s dependent-value evaluation to support a `types.Bool` dependent** touches shared validator plumbing used by other resources (string-typed dependents today, e.g. Kibana dashboard panel/mode validators). Mitigation: add the bool case alongside the existing string case rather than replacing it, and cover it with a unit test scoped to the new `force_merge_on_clone`/`force_merge_index` usage; existing string-dependent call sites are unaffected since they don't exercise the new code path.

## Open questions

None blocking — all four questions from the prior research run were answered by `@tobio`. Two small implementation-detail items remain:
